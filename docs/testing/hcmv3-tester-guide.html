Module 1

Access and login

Getting into the system as the two different kinds of account. Do these before anything else — every later test starts by logging in.

Test 1

Log in as Host

What this screen is. HCMv3 serves several companies from one application. Each company is called a tenant. The login page has a line above the form showing which tenant you are signing in to.

What Host means. Host is the top-level administrator who sits above all tenants. The Host does not belong to any company — it is the account that creates and manages the tenants themselves.

Steps

  1. Open the application URL in your browser.
  2. Look at the line above the login form. It should read “Current tenant: Not selected”. If it shows a tenant name instead, click Change, clear the box, and Save.
  3. Enter the user name and password below.
  4. Click Log in.

Test 4

Switch between tenants

What this is. There are two ways to move between companies, and they are used in different situations. Test both.

Method A is used before you log in. Method B is used by the Host to step inside a company without knowing its password.

Method A — switch on the login page

  1. Log out if you are signed in.
  2. Above the login form, click Change next to Current tenant.
  3. Type TEST01 and click Save.
  4. The line now reads “Current tenant: TEST01”. Log in with that tenant's own user name and password.
  5. To switch again, log out and repeat with a different tenancy name. Leave the box empty to go back to Host.

Method B — Host steps into a tenant

  1. Log in as Host and go to Administration → Tenants.
  2. On the row for TEST01, open the Actions menu.
  3. Click Login as this tenant.
  4. A Select a user dialog opens. Pick the tenant's admin user.
  5. To come back, open your user menu at the top right and click Back to my account.

Expected result

  • Method A: you land in the tenant you named, and see only that company's data.
  • Method B: you land inside TEST01 without typing its password, and the menu changes to the tenant menu — Tenants and Editions disappear.
  • Back to my account returns you to the Host, with the Host menu restored.

Test 5

What this screen is. The Tenants list shows every company in the system. From here the Host can search them, switch one off temporarily, or remove it.

Deactivate vs delete. Deactivating blocks everyone in that company from logging in, but keeps the data and can be undone. Deleting removes the tenant from the list.

Part 1 — View all tenants

  1. Log in as Host and go to Administration → Tenants.
  2. Check the list shows every tenant, including Default and TEST01.
  3. Type TEST01 into the search box and press Enter. Only that row should remain.
  4. Clear the search box and press Enter to bring the full list back.

Test 7

Create a role in a tenant

What this screen is. A role is a named set of permissions. Instead of granting screens to each person one by one, you build a role once — HR Officer, say — tick what it may do, then give that role to as many users as you like.

Roles belong to one company. A role you create here exists only in this tenant. Each company starts with Admin, User and Candidate already made.

Steps

  1. Log in to the Default tenant as admin.
  2. In the left menu, go to Administration → Roles.
  3. Click Create new role.
  4. In Role name, type TestRole.
  5. Leave the Default checkbox unticked.
  6. Click the Permissions tab at the top of the same window.
  7. Tick a few permissions you can recognise later — for example the view permissions under Employees.
  8. Click Save.

What “Default” means. Ticking it makes every new user get this role automatically. Leave it unticked for a test role, or every user you create afterwards picks it up.

Permission changes need a page refresh. After changing permissions, the affected user must reload the page — or log out and back in — before the menu updates. A menu that has not changed yet is not a bug; refresh first, then judge.

Then check the role works

  1. Go to Administration → Users and open testuser1 from Test 6 with Actions → Edit.
  2. On the Roles tab, tick TestRole and Save.
  3. Log out, then log in as testuser1 / Test@12345.
  4. Check the menu now shows the screens you granted in step 7.

Expected result

  • TestRole appears in the Roles list.
  • It can be ticked on a user's Roles tab.
  • After logging in, testuser1 can reach the screens granted to TestRole and nothing beyond them.
  • Reopening the role shows the same permissions you ticked — they were saved.

Test 8

Assign permissions to a role

What this screen is. The Permissions tab inside a role is a tree of everything the system can do, with a tickbox against each item. What you tick here is exactly what people holding that role can reach.

How the tree is arranged. Each screen is a parent, and the actions on it — Create, Edit, Delete — sit underneath as children. Granting someone the right to open a screen is separate from granting them the right to change anything on it.

Part 1 — Grant a permission

  1. Log in to the Default tenant as admin.
  2. Go to Administration → Roles.
  3. On the TestRole row, open Actions and click Edit.
  4. Click the Permissions tab.
  5. Type a screen name into the search box to find it quickly, or use Expand all to open the whole tree.
  6. Tick the permission for a screen the role does not have yet.
  7. Click Save.

Ticking a parent ticks everything under it. Tick a screen's top-level box and all its Create, Edit and Delete children are selected too.

Ticking a child does not tick its parent. If you tick only Create and leave the screen itself unticked, the user may not be able to open the screen at all. Tick the parent as well when you want a screen usable.

Part 2 — Check it took effect

  1. Log out and log in as testuser1 / Test@12345 in the Default tenant.
  2. Check the newly granted screen now appears in the menu and opens.

Part 3 — Remove a permission

  1. Log back in as admin.
  2. Open TestRole again, go to Permissions, and untick the permission you granted in Part 1.
  3. Click Save.
  4. Log in as testuser1 again and check the screen has gone from the menu.
  5. Try to open that screen by pasting its address into the browser bar.

Always refresh before judging. Permission changes do not reach an already-open page. Log out and back in — or reload — before deciding a change did not work.

Expected result

  • Reopening the role shows exactly the permissions you ticked — nothing added, nothing lost.
  • After granting, testuser1 sees the screen in the menu and can open it.
  • After removing, the screen disappears from the menu.
  • Pasting the removed screen's address directly is refused with a not-authorized message — it must not open anyway.
Result: Pass Fail Notes:

Test 9

Assign permissions to a single user

What this screen is. Permissions normally come from a person's role, as in Test 8. This screen lets you grant something to one person only, without changing the role or affecting anyone else who holds it.

When it is used. One person needs an extra screen that the rest of their team should not get. These are called special permissions, and they sit on top of whatever the role already gives.

Part 1 — Grant a permission to one user

  1. Log in to the Default tenant as admin.
  2. Go to Administration → Users.
  3. On the testuser1 row, open Actions and click Permissions.
  4. A permission tree opens, same as the one on a role. Tick a screen that TestRole does not grant.
  5. Click Save.
  6. Log out and log in as testuser1 / Test@12345.
  7. Check the extra screen now appears in the menu and opens.

Part 2 — Check nobody else was affected

  1. Log back in as admin.
  2. Open Administration → Roles, edit TestRole, and look at its Permissions tab.
  3. The screen you granted to testuser1 should not be ticked here.

This is the point of the test. A permission given to one user must not quietly appear on the role. If it does, everyone holding that role just gained access they were never meant to have.

Part 3 — Reset special permissions

  1. Go back to Administration → Users.
  2. On testuser1, open Actions → Permissions again.
  3. Click Reset special permissions.
  4. Click Save.
  5. Log in as testuser1 and check the extra screen has gone, while the screens from TestRole are still there.

What Reset does. It clears everything granted to this person individually and drops them back to exactly what their roles give. It does not remove their roles.

Refresh before judging. As in Test 8, an already-open page keeps the old permissions until it is reloaded.

Expected result

  • testuser1 gains the extra screen after Part 1, and it opens.
  • TestRole is unchanged — the grant stayed on the one user.
  • After Reset, the extra screen is gone but the role's screens remain.
  • At every stage, a screen missing from the menu also refuses to open when its address is pasted into the browser bar.
Result: Pass Fail Notes:

Host settings

The Host's own Settings page, one test per tab. These settings affect the whole installation, so work through them carefully.

Read this before starting Module 4. Every test here changes a live setting. Before you change anything, write down the value that was already there, and put it back when the test is finished. The Notes line on each test is a good place for it.

These tests ask the server directly, the way an attacker would, using another company's record numbers. These are the most important tests in the guide — a failure in any of them blocks release.

What you need. Postman (free, from postman.com), the API address of the server — ask whoever runs it, it usually ends in the same domain as the application — and the two test companies S180 and SCC, each with its own admin and at least one employee.

Write {API} below as your API address, for example https://api.yourcompany.com. Every request uses Body → raw → JSON where a body is shown.

Test 180

Get a login token for each company

What a token is. When you sign in, the server gives your browser a long code that proves who you are. Every later request carries it. Here you get that code by hand, once for each company.

Part 1 — Find each company's number

  1. In Postman, create a POST request to {API}/api/services/app/Account/IsTenantAvailable with body {"tenancyName": "S180"}. Send.
  2. In the response, write down result.tenantId as Tenant A id.
  3. Repeat with "SCC" and write it down as Tenant B id.

Part 2 — Sign in to each

  1. Create a POST request to {API}/api/TokenAuth/Authenticate.
  2. Under Headers, add Abp.TenantId with the value of Tenant A id.
  3. Body: {"userNameOrEmailAddress": "admin", "password": "…"} with S180's admin password. Send.
  4. Copy result.accessToken and save it as Token A.
  5. Repeat with Tenant B id and SCC's admin password, and save Token B.

Part 3 — Find one of company B's employees

  1. Create a POST request to {API}/api/services/app/Employees/GetAll, body {}.
  2. Under Authorization, choose Bearer Token and paste Token B. Send.
  3. Write down the id of one employee in result.items as Employee B id, and their name.
  4. Send the same request with Token A, and write down the totalCount as Company A count.

Expected result

  • Both companies return a number, and both sign-ins return a token.
  • Token B lists only SCC's employees; Token A lists only S180's.

Tokens are passwords. Do not paste them into chat messages or bug reports. They stop working after a while — if later requests start failing with 401, sign in again.

Test 181

Read, change or delete another company's employee

The attack. You are signed in as company A, and you know the record number of an employee in company B. Can you read that employee, change them, or delete them? The answer must be no, every time.

Part 1 — Read

  1. GET {API}/api/services/app/Employees/GetEmployeeForEdit?Id=Employee B id, with Token A.

Part 2 — Change

  1. Send the same GET with Token B, and copy the whole result.employee object from the response.
  2. Change the first English name in it to HACKED.
  3. POST it as the body to {API}/api/services/app/Employees/CreateOrEdit, with Token A.
  4. Sign in to the application as SCC's admin and look at that employee's name.

Part 3 — Delete

  1. DELETE {API}/api/services/app/Employees/Delete?Id=Employee B id, with Token A.
  2. Check in the application that the employee still exists in SCC.

Expected result

  • Read returns an error — usually saying the record was not found — and none of the employee's details.
  • Change is refused, and the employee's name in SCC is unchanged.
  • Delete is refused, and the employee is still in SCC.

If any of the three succeeds, stop testing and report it immediately as a critical fault, with the request, the response, and the time. Undo any change through SCC's admin.

Test 182

Pretend to be the other company

The attack. The request says which company it belongs to in a header, Abp.TenantId. What if someone signed in to company A simply changes that header to company B?

Steps

  1. POST {API}/api/services/app/Employees/GetAll, body {}, with Token A — and add a header Abp.TenantId set to Tenant B id.
  2. Look at the names and the totalCount.
  3. Send the same request again with {"maxResultCount": 1000} as the body.

Expected result

  • The response contains only company A's employees — the token decides the company, not the header — or the request is refused.
  • totalCount equals Company A count from Test 180, even when asking for 1,000 records.
  • If any company B name appears, stop and report it at once.

Test 183

No token, the wrong kind of token, and an old token

Three more doors to check. A request with no sign-in at all, a company user asking for a Host-only list, and a token from a company that has since been switched off.

Steps

  1. No token. POST {API}/api/services/app/Employees/GetAll with body {} and no Authorization.
  2. Host-only list. GET {API}/api/services/app/Tenant/GetTenants with Token A.
  3. Old token. As Host, make SCC inactive (Test 5). Then send Employees/GetAll again with Token B. Make SCC active again afterwards.

Expected result

  • No token — refused as not signed in (401), with no data.
  • Host-only list — refused as not permitted (401 or 403); the list of companies is not returned.
  • Old token — once SCC is inactive, its token no longer returns data. Record exactly what happened: if the token keeps working until it expires, note how long.

Release rule. Tests 181 and 182 must pass before HCMv3 goes live for more than one company. A failure in either is not a bug to schedule — it is a stop.
